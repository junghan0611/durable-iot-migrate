# 경계 — 이 리포가 소유하는 것과 소유하지 않는 것

> 이 문서가 경계의 정본이다. 다른 문서가 이것과 어긋나면 이 문서가 이긴다.

작은 코어를 지키는 방법은 "작게 짜자"고 다짐하는 것이 아니라 **선을 긋고 그 선을 문서로
못 박는 것**이다. 부채는 코드가 아니라 소유권의 흐릿함에서 들어온다.

---

## 1. 소유한다

| 소유물 | 내용 |
|---|---|
| **Place 모델** | area 위계, 기기의 area 소속, 집합 참조(`(cap-set :area … :cap …)`) 문법과 접기 규칙 |
| **Recipe IR** | Expr 맵 구조, 표준 op 집합, 네임스페이스 확장 규약 |
| **컴파일 제약** | 허브 실행 가능성 게이트 — 무엇을 거부하고 무엇을 통과시키는가 |
| **컴파일 산출물 포맷** | 허브·서버가 읽는 실행 표현 (bounded, 정적 크기) |
| **의미 검증** | `structural-equiv?` · `equiv?` · `diff` · 결정론적 시뮬레이션 |
| **호환 표면** | 외부 플랫폼 파서·에미터 (HA 우선), 미지원 항목 **거부 + 카운트** 규율 |

## 2. 소유하지 않는다

| 남의 것 | 누구 것인가 |
|---|---|
| device transport — MQTT topic, QoS, retain, 페이로드 wire | 허브 ↔ 서버 계약 |
| capability taxonomy — `switch`/`power`/… 어휘와 정규화 | device 계약 |
| 기기 발견·페어링·삭제 | 허브 |
| 허브 생명주기 — 부팅, 온라인 판정, 복구 | 허브 |
| 계정·인증·소유권 | 서버 |
| UI, 화면, 컨트롤 렌더링 | 앱 |
| 워크플로 엔진, 큐, 브로커 | 아무도 — **필요 없게 만드는 것이 목표다** |

이 리포는 위의 것들을 **참조는 하되 재해석하지 않는다.** capability 이름이 필요하면
device 계약의 것을 그대로 쓴다. 여기서 새 taxonomy를 만들면 두 개의 진실이 생긴다.

## 3. 왜 하필 여기서 자르는가

세 가지 기준으로 잘랐다.

**(1) 순수한 것과 부작용 있는 것.** 이 리포의 모든 것은 데이터 → 데이터 변환이다.
소켓도, 파일도, 시계도 없다. 시뮬레이션조차 주입된 시간축 위에서 돈다.
그래서 테스트에 mock이 필요 없고, 결과가 재현된다.

**(2) 한 번 정하는 것과 매 순간 도는 것.** 레시피는 사람이 만들 때 한 번 컴파일된다.
허브는 그것을 100ms마다 평가한다. **컴파일은 여기, 평가는 저기.**
이 선을 지키면 허브에 파서도 질의 엔진도 안 생긴다.

**(3) 언어 경계.** 허브는 Zig, 서버는 Go, 앱은 Flutter다. 아무도 Clojure를 링크하지 않는다.
이 리포는 **산출물과 스펙**을 내보내고, 각자 자기 언어로 읽는다.
Clojure는 그 산출물을 만들고 검증하는 데 쓰인다 — 런타임 의존이 아니다.

## 4. 실행 진실의 규율

컴파일 산출물을 받아 실행하는 쪽(허브든 서버든)이 지켜야 할 세 줄이다.
이 리포는 이 규율을 **전제하고** 시뮬레이터를 만든다.

1. **dispatch는 완료가 아니다.** action을 보냈다는 사실은 상태가 아니다.
2. **완료의 진실은 관측된 state다.** 성공 응답을 받고도 기기가 안 바뀌었으면, 진실은 관측 쪽이다.
3. **재부팅은 정상 경로다.** 실행 상태는 고정 크기로 직렬화되고, 다음 부팅에서 이어진다.
   이어질 수 없는 레시피는 컴파일 단계에서 거부한다.

## 5. 런타임 배치 — 열린 결정 (지금 칸 아님)

> **이 결정은 중간 폼이 성립한다는 증거가 나온 뒤에 연다** (`NEXT.md`). 여기 적어두는 이유는
> 선택지를 잊지 않기 위해서지, 지금 고르기 위해서가 아니다.

컴파일 산출물을 **누가 평가하는가**는 아직 닫히지 않았다.

| 안 | 실행 위치 | 장점 | 대가 |
|---|---|---|---|
| A | 서버 | 가장 빠르게 닫힌다. 로그·디버깅이 쉽다 | 인터넷 끊기면 집이 멎는다 |
| B | 허브 | 오프라인 자율. 지연이 낮다 | 구현이 무겁고 관측이 어렵다 |
| C | 둘 다 (같은 산출물) | 서버는 광역·클라우드 의존 레시피, 허브는 로컬 필수 레시피 | 두 런타임의 의미 동치를 계속 증명해야 한다 |

**권고: 목표는 C, 첫 런타임은 A. 단, 제약은 지금부터 B 기준으로 강제한다.**

이유는 하나다 — 나중에 허브로 옮길 때 **IR을 갈아엎지 않기 위해서**다.
서버에서만 돌 생각으로 IR을 열어두면 템플릿이 들어오고, 그때는 이미 늦다.
C의 의미 동치는 이 리포의 `equiv?`가 감당할 자리이기도 하다.

## 6. 이 리포에 들어오면 안 되는 것

- 임의 코드 평가 — 템플릿 엔진, 스크립트 런타임, `eval`
- 네트워크 I/O — 어떤 플랫폼의 API도 여기서 호출하지 않는다
- 실시간 시계 — 시간은 항상 주입된다
- 워크플로 서버 의존 — 집 안에 브로커를 하나 더 두지 않는다
- device capability의 재정의 — 남의 어휘를 여기서 고치지 않는다
